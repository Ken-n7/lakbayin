# Case studies and visibility: how real games show many players on one map, and what players notice

Scope note: researched 2026-10-08. Source labels: **[official]** = developer or vendor docs; **[fan/RE]** = fan server, decompiled or reverse-engineered code; **[3rd-party]** = press, tutorial or academic; **[weak]** = forum/Reddit/community post. Project numbers used in the inferences (30 to 40 phones, 6 teams of 5, ~165 msg/s for 30 players, 1.0 to 1.2 s observed delay) come from the task brief, not from these sources.

## 1. .io games: tick/send rates, view culling, binary protocols, server architecture

### Takeaway
.io games send other players' positions at about 25 to 30 updates per second, but **only for objects inside each player's view box**, and they draw other players about 100 ms in the past with interpolation. Each game server holds one shared world: about 600 players per server in slither.io. They save bandwidth by culling what each player receives and by using compact binary deltas, not by sending updates less often.

### Cited Findings
- Victor Zhou's .io tutorial: the server simulates at 60 Hz but sends an update "every other time `update()` is called", which gives "30 game updates per second", and the reason given is "To save bandwidth. 30 game updates per second is plenty!" **[3rd-party tutorial]** — [Victor Zhou, part 2](https://victorzhou.com/blog/build-an-io-game-part-2/)
- The same tutorial sends each player only nearby objects: `nearbyPlayers = ... filter(p => p !== player && p.distanceTo(player) <= Constants.MAP_SIZE / 2)`, because "there's no need to include info about game objects far away from the player!" **[3rd-party tutorial]** — [Victor Zhou, part 2](https://victorzhou.com/blog/build-an-io-game-part-2/)
- The tutorial client renders other entities at "100 ms behind the server's game state" and linearly interpolates between the two updates around that time. Transport is socket.io with JSON payloads. **[3rd-party tutorial]** — [Victor Zhou, part 1](https://victorzhou.com/blog/build-an-io-game-part-1/)
- slither.io uses a binary protocol (version 11) with int8/int16/int24 fields and 3-byte client-bound headers. Movement packets come in two forms, absolute 16-bit positions ("g") or relative 8-bit deltas ("G"). **[fan/RE: ClitherProject reverse-engineering]** — [Slither.io-Protocol](https://github.com/ClitherProject/Slither.io-Protocol/blob/master/Protocol.md)
- slither.io culls by view: the snake add/remove packet is "Sent when another snake enters range" and "Sent when another snake leaves range (that is, close enough to be drawn on screen) or dies". Add/Remove Sector packets ("W"/"w") manage the active sectors around each player. **[fan/RE]** — [Slither.io-Protocol](https://github.com/ClitherProject/Slither.io-Protocol/blob/master/Protocol.md)
- slither.io's developer, Steven Howse: "The hardest part of development was making each server stable enough to handle 600 players at a time". He built the game once "WebSockets were stable enough for an HTML5 game". **[official, interview]** — [Pocket Gamer interview](https://www.pocketgamer.com/articles/070063/interview-the-future-of-slither-io-and-tips-direct-from-the-developer/)
- Ogar, an open-source agar.io server clone, runs its main loop on 40 ms ticks (25 Hz). Its config comment reads "spawnInterval ... (1 tick = 50 ms)", and the leaderboard updates every 4 ticks. Each player gets a view box (`serverViewBaseX: 1024`, `serverViewBaseY: 592`, scaled by cell size; comment: "high values may cause lag"). Only `visibleNodes` are sent, and the view box is recomputed every 5 ticks. **[fan/RE: clone, not the official agar.io server]** — [ogarproject/ogar GameServer.js](https://github.com/ogarproject/ogar/blob/master/src/GameServer.js); [PlayerTracker.js](https://github.com/ogarproject/ogar/blob/master/src/PlayerTracker.js)
- diep.io is C++ compiled to WebAssembly. Its protocol was reverse-engineered by the diepssect project (2017 onward). No reliable update-rate figure was found. **[fan/RE]** — [cx88/diepssect](https://github.com/cx88/diepssect)

### Inferences
- The .io pattern for "everyone on one big map" is **server-side view culling plus a high rate for what is visible**, not "everyone, everywhere, live". For NumXventure that means option (c), with a per-viewer filter on the server.
- An interpolation delay of ~100 ms is the industry norm for showing other players smoothly at 25 to 30 Hz. A 1.0 to 1.2 s delay is roughly 10 times that. It most likely comes from the relay path and buffering, not from anything smooth display requires.
- .io games keep their high rates because collision and combat with others is the whole game. NumXventure has no such interaction, so it needs far less than they do.

### Gaps
- No official agar.io, diep.io, krunker or surviv.io tick-rate or culling documentation was found. The agar.io figures come from a fan clone only. No sources were found for krunker or surviv.io.
- No official slither.io server tick rate or per-client bandwidth figure was found.

## 2. Shared-avatar spaces: Gather, Club Penguin, Habbo, Toontown, Roblox, Pokémon GO, Animal Crossing

### Takeaway
Social avatar spaces cap or split their crowds: Gather allows 500 per space and tells users to split, Prodigy about 200 per world, Gimkit 2D 60, Minecraft Education 30. They also send movement cheaply. Club Penguin (per fan-server code) sends **one message per click, holding the destination**, and every client walks the penguin there. Disney's Panda3D engine (Toontown) broadcasts position at **5 Hz by default, only when it changes**, and shows others **0.2 s behind**.

### Cited Findings
- **Club Penguin (fan server Houdini):** the move handler `handle_set_player_position(p, x, y)` stores x,y and calls `p.room.send_xt('sp', p.id, x, y)`, one broadcast to everyone in the room per move command. Emotes and actions are separate, rate-limited (`@handlers.cooldown(1)`) one-shot messages. **[fan/RE: solero/houdini private-server emulator]** — [houdini/handlers/play/player.py](https://github.com/solero/houdini/blob/master/houdini/handlers/play/player.py)
- A Club Penguin private-server client library exposes movement as a single `walk x y` command, which matches the click-a-destination model. **[fan/RE]** — [CPPS-PCL](https://github.com/turicfr/CPPS-PCL)
- **Toontown / Panda3D** (Disney's engine, later open-sourced): `startPosHprBroadcast(self, period=.2, ...)` broadcasts position every 0.2 s by default (5 Hz). The C++ broadcaster sends only the changed components (`only_changed(... F_new_x | F_new_y)` → `d_setSmXY`). When the avatar stops, it sends a single `d_setSmStop()` and then goes quiet. **[official engine source; Toontown's own values unverified]** — [DistributedSmoothNodeBase.py](https://github.com/panda3d/panda3d/blob/master/direct/src/distributed/DistributedSmoothNodeBase.py); [cDistributedSmoothNodeBase.cxx](https://github.com/panda3d/panda3d/blob/master/direct/src/distributed/cDistributedSmoothNodeBase.cxx)
- Panda3D receivers render others with `smooth-lag` = 0.2 s by default (`smooth-prediction-lag` 0.0, `smooth-max-future` 0.2). The docs: without prediction, "avatars will be lagged by a certain factor to achieve smooth motion"; with prediction, they are drawn "as nearly as possible in their current position, by extrapolating from old position reports." **[official]** — [DistributedSmoothNode.py](https://github.com/panda3d/panda3d/blob/master/direct/src/distributed/DistributedSmoothNode.py); [Panda3D manual: Distributed Smooth Node](https://docs.panda3d.org/1.10/cpp/programming/networking/distributed/distributed-smooth-node)
- **Gather:** price is set by "Space Capacity: the maximum number of concurrent users". The free plan allows 10 and paid plans up to 500. **[official]** — [Gather support: pricing and capacity](https://support.gather.town/hc/en-us/articles/20564757169684)
- Gather: "If you're planning a large event on Gather 1.0 (500+ people), you'll need to create multiple spaces", which "will improve performance for attendees". It recommends a "Hub and Spokes" layout of identical spaces. **[official]** — [Gather support: connect multiple spaces](https://support.gather.town/articles/6044193155-connect-multiple-spaces-for-a-500-person-event)
- Gather exposes a websocket game-server API with a `playerMoves` event, so third-party clients receive per-move events. **[weak: community forum]** — [Gather forum: Go Kart/Movement example](https://forum.gather.town/t/go-kart-movement-example-with-websocket-api/47); [Gather forum: API help](https://forum.gather.town/t/looking-for-help-connecting-to-the-api-and-also-which-event-to-use-to-gate-access-to-a-room/31)
- A Gather engineer's write-up on rebuilding Gather's world covers map data models (Firestore documents, three divergent map tools), not avatar sync. **[official-ish: engineer's Substack]** — [Evangeline Cheng, "Rebuilding Gather's virtual world"](https://evangelinecheng.substack.com/p/rebuilding-gathers-virtual-world)
- A Gather user manual says you can play on "3Mbps down/1Mbps up; however, you will experience more lag as you connect to more people." **[3rd-party: university manual]** — [Tohoku Univ. Gather User Manual (PDF)](https://web.tohoku.ac.jp/ged/wp-content/uploads/2021/11/Gather-User-Manual.pdf)
- **Roblox:** instance streaming loads and unloads content around each player's "replication focus" (default the character). Defaults are `StreamingMinRadius` 64 and `StreamingTargetRadius` 1024 studs. With streaming, "the server can spend less time and bandwidth synchronizing changes", and "Client-side physics simulation ... only occurs in streamed areas". **[official]** — [Roblox: Instance streaming](https://create.roblox.com/docs/workspace/streaming); [streaming.md](https://create.roblox.com/docs/en-us/workspace/streaming.md)
- Roblox: "a single player with nine dynamically moving foci could generate server networking and streaming processing comparable to ten players". So per-viewer interest areas cost the server work in proportion to their number. **[official]** — [Roblox: Instance streaming](https://create.roblox.com/docs/workspace/streaming); [DevForum: Multiple Replication Foci](https://devforum.roblox.com/t/new-instance-streaming-feature-multiple-replication-foci/3848736)
- **Habbo (fan emulators):** walking is click-a-tile with server pathfinding. "The person who clicks first will walk first", and steps go diagonal first, straight last. **[weak/fan: Arcturus emulator issue tracker]** — [Arcturus issue #294](https://bitbucket.org/Wesley12312/arcturus/issues/294/random-click-between-both-users); [Arcturus issue #1475](https://bitbucket.org/Wesley12312/arcturus/issues/1475/incorrect-pathfinder-behaviour)
- **Pokémon GO:** Niantic said third-party live maps "consumed too many server resources" and acted "similar to DDoS attacks". This concerns map scraping, not avatar visibility. **[3rd-party press]** — [PCWorld](https://www.pcworld.idg.com.au/article/604711/some-pok-mon-go-maps-jeopardy-niantic-admits-blocking-scrapers/); [Business Insider](https://www.businessinsider.in/pokemon-gos-developers-are-defending-killing-off-a-key-feature/articleshow/53504633.cms)

### Inferences
- Club Penguin's pattern is option (e). It is the closest real precedent for NumXventure: a 2D kids' social map, no collisions between players, rooms of dozens of avatars, one small message per click instead of a stream.
- The Panda3D/Toontown defaults (5 Hz, send only on change, a "stop" message, 0.2 s display lag) show that a kids' MMO considered 5 Hz with 200 ms smoothing good enough for other avatars. That is 5 to 6 times less delay than NumXventure's current 1.0 to 1.2 s.
- Gather, Prodigy and Gimkit all cap concurrent avatars per shared space. NumXventure's 40 is well inside every cap found, so size alone needs no exotic architecture.

### Gaps
- No official Gather engineering post was found on avatar sync rates, interest management, or whether clients receive all avatars or only nearby ones.
- No reliable source was found for the Habbo room tick (the commonly repeated "500 ms room cycle" could not be verified), for Club Penguin's original (Disney) server update rates, or for Club Penguin Rewritten.
- No technical source was found for Animal Crossing online movement sync or Pokémon GO raid lobbies. Pokémon GO's choice not to show other trainers on the map was not documented in any source found.

## 3. Mobile party, social-deduction and classroom quiz games: what delay they tolerate

### Takeaway
Among Us, a casual social game of 4 to 15 players, sends each player's position **at most every 0.1 s and only when it moved**, smooths on the receiver, and snaps if the error exceeds 5 units. That figure comes from decompiled code. Classroom games with walking avatars cap rooms low: **Gimkit 2D modes at 60** (500 for its non-2D modes), citing connection reliability, and Minecraft Education at 30. Mediatonic found Fall Guys players perceived about twice as many opponents as were actually present.

### Cited Findings
- **Among Us (decompiled client, older version):** `CustomNetworkTransform` has `sendInterval = 0.1f`, `snapThreshold = 5f` and `interpolateMovement = 1f`. The owner marks itself dirty only `if (this.HasMoved())`, and `InnerNetClient.MinSendInterval = 0.1f`. Non-owners steer toward the target position with velocity scaled by `interpolateMovement / sendInterval`, capped at the local player's speed, and snap if more than `snapThreshold` away. **[fan/RE: decompiled assets in polusgg/assets-unity]** — [CustomNetworkTransform.cs](https://github.com/polusgg/assets-unity/blob/master/Assets/OfficialAssets/Scripts/CustomNetworkTransform.cs); [InnerNetClient.cs](https://github.com/polusgg/assets-unity/blob/master/Assets/OfficialAssets/Scripts/InnerNet/InnerNetClient.cs)
- Among Us movement payload: a uint16 sequence id, a Vector2 position and a Vector2 velocity. `SnapTo` is a separate RPC for teleports (vents, spawn selection). **[fan/RE: roobscoob/among-us-protocol]** — [CustomNetworkTransform doc](https://github.com/roobscoob/among-us-protocol/blob/master/05_innernetobject_types/10_customnetworktransform.md); [SnapTo doc](https://github.com/roobscoob/among-us-protocol/blob/master/04_rpc_message_types/21_snapto.md)
- Among Us servers are relays ("Impostor is an open source reimplementation of the Among Us Server"). In 2020, Innersloth's North America region took the heaviest load and players were told to switch regions. Rushed anti-cheat server changes caused bugs. **[fan/RE + official devlog + press]** — [Impostor](https://github.com/AeonLucid/Impostor); [Innersloth devlog "Small Patch and Small Roadmap"](https://innersloth.itch.io/among-us/devlog/192737/small-patch-and-small-roadmap); [PC Invasion](https://www.pcinvasion.com/?p=238294)
- **Fall Guys:** when Mediatonic asked players how many Fall Guys they felt they were playing with, "their response was often twice as high as the actual number". They dropped from 100 to 60 because "100 players made even our simplest levels too crowded and ultimately less fun" (Feb 2020). **[3rd-party press quoting official post]** — [PCGamesN](https://www.pcgamesn.com/fall-guys/player-count); the original official URL (fallguys.com/news/the-starting-lineup) now returns 404
- **Gimkit:** "We have a separate hard limit of 60 students for all 2D game modes", compared with 500 for live games. The reason given: "a faster and more reliable connection will be required to keep up with all the players". **[official]** — [Gimkit Help: Player maximums](https://help.gimkit.com/en/article/player-maximums-18mbcz0/); [Gimkit Help: 2D game modes](https://help.gimkit.com/en/article/2d-game-modes-1fhidpg/)
- **Minecraft Education:** "up to 30 children in one world". Classes larger than 30 must split, and teachers have asked for a higher cap. **[3rd-party/education + weak community request]** — [Microsoft UK Stories](https://ukstories.microsoft.com/2016/11/03/minecraft-education-edition-released-help-children-learn-schools/); [Minecraft Edu community: increase limit from 30](https://educommunity.minecraft.net/hc/en-us/community/posts/360072427031)
- **Prodigy:** 90 worlds, "Each world can currently hold 200 players max". Players choose the same world to meet friends. **[official per search snippet; the page now returns 404, unverified live]** — [Prodigy blog: multiplayer worlds](https://www.prodigygame.com/main-en/blog/prodigy-game-update-multiplayer-worlds)

### Inferences
- Among Us is the closest mobile analogue: a top-down 2D map, phones, a casual social group. Its ceiling is 10 Hz, and only while moving, so idle players cost nothing. NumXventure heroes stand still at towers while the team answers, so a "send only while moving" rule alone should cut traffic sharply.
- The Fall Guys finding suggests a crowd does not need exact positions or full counts to feel full, which supports low-rate or ghost rendering of other teams.
- Gimkit 2D is the closest classroom analogue (walking Gims, live class sessions). Its 60 cap is about NumXventure's size. No public source says how Gimkit syncs or culls movement.

### Gaps
- No official Innersloth/Hazel post with update rates was found. The 0.1 s figure comes from decompiled code of an older client version and may have changed.
- No Fall Guys, Stumble Guys or Brawl Stars/Supercell netcode post with rates was found; Fall Guys rates appear only in player forums ("20-30hz"), which is too weak to use.
- No technical source was found on Gimkit 2D or Kahoot sync. Kahoot has no shared walking map, so it does not apply directly.

## 4. MMO practice: interest management, LOD for distant players, crowd systems

### Takeaway
MMOs send each player only the state that matters to them (area of interest), and they rank updates so important objects go every packet while minor ones go less often. When crowds are too big, they **show fewer or simpler models instead of hiding players outright**. Guild Wars 2 dropped server-side culling in 2013 after it made players pop in late. FFXIV lets players cap visible characters and hide crowds around quest NPCs.

### Cited Findings
- Boulanger, Kienzle and Verbrugge (NetGames 2006): MMOs "employ sophisticated interest management techniques that only send relevant state changes to each player". Interest management that accounts for obstacles reduces update messages "by up to a factor of 6", and cheap tile-based schemes approximate ideal visibility-based interest management at very low cost. **[3rd-party academic]** — [Boulanger et al. 2006 (PDF)](https://www.sable.mcgill.ca/~clump/papers/boulanger-06-comparing.pdf)
- Glenn Fiedler's priority accumulator: each frame, each object's priority is added to its accumulator, objects are sorted, and packets are filled in order up to a bandwidth budget. Sent objects reset to zero while skipped ones keep their score, so low-priority objects still get updates, just less often. His example gives the player's own object priority 1,000,000, interacting objects 100 and resting objects 1. **[3rd-party, developer blog]** — [Gaffer On Games: State Synchronization](https://gafferongames.com/post/state_synchronization/)
- Source engine (Valve): default interpolation "lerp" of 100 ms (`cl_interp 0.1`), so that even if one snapshot is lost there are still two to interpolate between; delta compression sends only the differences from the previous state. **[official wiki, via search; direct fetch returned 403]** — [Valve Developer Wiki: Source Multiplayer Networking](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking); [Valve: Interpolation](https://developer.valvesoftware.com/wiki/Interpolation)
- **Guild Wars 2:** culling once "only rendered characters within a certain radius". In WvW it caused late pop-in that gave stealthed players "a few seconds of extra invisibility". ArenaNet removed it from WvW on 26 March 2013 and from PvE on 20 August 2013, replacing it with client-side "Character Model Limit" and "Character Model Quality" settings that use generic models. **[fan wiki]** — [Guild Wars 2 Wiki: Culling](https://wiki.guildwars2.com/wiki/Culling)
- GW2 players call Character Model Limit "the biggest fps killer" and lower it during world bosses and WvW. **[weak: community guides]** — [Hardstuck performance guide](https://hardstuck.gg/gw2/guides/general/performance-improving-settings); [GW2 forum](https://en-forum.guildwars2.com/topic/98815-suggestion-character-model-limit-should-not-cull-npc-models)
- **FFXIV:** System Configuration → Display Limits has a "Character and Object Quantity" setting (Maximum/Normal/…/Automatic) and a separate "Character Display Range". Raising the range "may increase system load". **[official]** — [FFXIV UI Guide: character quantity](https://na.finalfantasyxiv.com/uiguide/faq/faq-other/setting_ch_quantity.html); [FFXIV UI Guide: display range](https://na.finalfantasyxiv.com/uiguide/faq/faq-other/setting_ch_displayrange.html)
- FFXIV Dawntrail added an option to hide players clustered around a quest NPC or object, because crowds made targets hard to find. **[3rd-party press]** — [VGC](https://videogameschronicle.com/guide/ffxiv-hide-players-quest-npc); [Destructoid](https://destructoid.com/how-to-hide-other-players-near-quest-npcs-in-ffxiv)

### Inferences
- The MMO toolkit maps onto NumXventure as: area of interest (team, or within camera), priority or rate by relevance (own team high, other teams low), and LOD (other teams as simpler ghosts or markers). Fiedler's accumulator is a ready-made way to give "teammates every tick, others when there is room" within one budget.
- The GW2 lesson: hiding players that matter to gameplay draws complaints, but showing them in less detail is accepted. Other teams' heroes in NumXventure have no gameplay effect, so lowering their detail is lower risk than GW2's case.
- The FFXIV lesson: 30 to 40 heroes piled on one tower will cover the tower. A hide or fade option for non-team heroes near the player's own tower may help on its own merits, regardless of network savings.

### Gaps
- No primary WoW source on player-cull settings was searched or found. The Valve page could not be fetched directly (403), so its figures come from search snippets of the official wiki.

## 5. Human perception: delay players notice for others vs themselves; smoothness vs teleporting

### Takeaway
Players must see their **own** movement instantly. Delay on **other** avatars is tolerated much better, especially in third-person or bird's-eye games without precise interaction. Claypool & Claypool (2006) put performance-degradation thresholds at 100 ms for first-person, 500 ms for third-person avatar games and 1000 ms for "omnipresent" games. Engine practice shows others about 100 to 200 ms in the past, and smoothness (interpolation instead of jumps) is what makes the delay invisible.

### Cited Findings
- Claypool & Claypool, "On Latency and Player Actions in Online Games" (WPI TR-06-13; CACM Nov 2006), Table 1: Avatar/First Person (FPS, racing), sensitivity **High, threshold 100 ms**; Avatar/Third Person (sports, RPG), **Medium, 500 ms**; Omnipresent (RTS, sim), **Low, 1000 ms**. They also write: "Online games that use the Avatar model ... are more sensitive to latency than games that use the Omnipresent model", and "player actions that are less precise or have looser deadlines tend to shift the curves ... to the right." **[3rd-party academic]** — [WPI tech report 06-13 (PDF)](https://ftp.cs.wpi.edu/pub/techreports/pdf/06-13.pdf); [CACM article](https://cacmb4.acm.org/magazines/2006/11/5798-latency-and-player-actions-in-online-games)
- From the same paper: Madden NFL (third-person) showed "no significant drop-off in performance until after 500 milliseconds". In EverQuest 2, 0 to 500 ms added "only an additional 5 seconds to about 2 minutes of combat". In Warcraft III, up to 3.5 s of latency increased build time "by at most 14 seconds", under 1%. **[3rd-party academic]** — [WPI TR 06-13](https://ftp.cs.wpi.edu/pub/techreports/pdf/06-13.pdf)
- Caveat: these thresholds measure how much latency degrades **the player's own task performance**. They do not measure how noticeable delay is on other players' avatars. — [WPI TR 06-13](https://ftp.cs.wpi.edu/pub/techreports/pdf/06-13.pdf)
- Gambetta, entity interpolation: "each player sees itself in the present but sees the other entities in the past". At 10 updates/s, others are shown 100 ms late, and "seeing other entities with a 100 ms delay isn't generally noticeable". Without interpolation the result is "very choppy movement, that is, discrete jumps every 100ms". **[3rd-party, widely used tutorial]** — [Gabriel Gambetta: Entity Interpolation](https://www.gabrielgambetta.com/entity-interpolation.html)
- Valve's Source engine buffers updates and plays them back smoothly ("prevents the jittery motion this would ordinarily lead to"), with a default 100 ms buffer. **[official]** — [Valve Developer Wiki: Interpolation](https://developer.valvesoftware.com/wiki/Interpolation)
- Panda3D/Toontown default display lag for others is 0.2 s; prediction can extrapolate toward the present instead. **[official engine source]** — [DistributedSmoothNode.py](https://github.com/panda3d/panda3d/blob/master/direct/src/distributed/DistributedSmoothNode.py)
- Perception of one's own avatar latency depends on motion speed: critical latencies are about 80 ms for medium and fast motion and about 120 ms for slow motion. This is VR self-avatar work, not about other players. **[3rd-party academic, via aggregator]** — [Nweon summary: "Influence of Motion Speed on the Perception of Latency in Avatar Control"](https://paper.nweon.com/?p=7993)
- Pantel & Wolf (NetGames 2002), "On the suitability of dead reckoning schemes for games", is the standard reference for predicting remote players between updates, and later work uses perception to set error thresholds. **[3rd-party academic, citation only; full text not read]** — [TU Braunschweig bib entry](https://www.ibr.cs.tu-bs.de/bib/xml/PaWo02a.xml); [Maynooth TWISSC 2006](https://mural.maynoothuniversity.ie/id/eprint/1348/)

### Inferences
- NumXventure's own hero must stay local and instant (it presumably already is). For other heroes, the game sits between Claypool's "third-person avatar" and "omnipresent" classes, and seeing others carries no deadline or precision demand. So 0.5 to 1 s of delay on others is unlikely to hurt play.
- The one place delay could become noticeable is **co-located comparison**. Students sit next to each other, so a classmate can say "I'm at tower 3 already" while their hero is still walking on your screen. No study measuring this was found; it is a reasoned risk, not a finding.
- Evidence and practice agree that smooth motion matters more than freshness: a ghost that glides 1 s late reads as "alive", while one that jumps every second reads as broken. Whatever lower rate is chosen, receivers should interpolate or animate along a path rather than snap.

### Gaps
- No study was found that measures noticeable delay on **other players'** avatars in casual or non-competitive games, or in co-located classroom play.
- No study was found that directly compares "smooth but late" with "fresh but jumpy" for remote avatars; the support is engineering practice (Gambetta, Valve, Panda3D).

## 6. Design options for NumXventure: savings and losses, with evidence

### Takeaway
Each cheaper design has a real precedent. Toontown sent only on change at 5 Hz, Among Us at 10 Hz while moving, Club Penguin one message per click, .io games and Roblox cull by view, and MMOs (GW2, FFXIV, Fiedler) use per-relevance rate and LOD. The estimated cuts in updates each phone must receive range from about 70% (b) to about 99% (d). The main costs are fidelity of free roaming (d) and, for (c), a per-viewer server. Option (e) and a "send only on change" rule also attack the delay directly, because receivers no longer need a deep buffer.

### Cited Findings
- (a) Everyone live is the .io and Among Us pattern: 25 to 30 Hz with view culling in .io games, and 10 Hz while moving in Among Us. **[3rd-party, fan/RE]** — [Victor Zhou](https://victorzhou.com/blog/build-an-io-game-part-2/); [Ogar](https://github.com/ogarproject/ogar/blob/master/src/GameServer.js); [Among Us CNT (decompiled)](https://github.com/polusgg/assets-unity/blob/master/Assets/OfficialAssets/Scripts/CustomNetworkTransform.cs)
- (b) Rate or priority by relevance is Fiedler's priority accumulator (high priority every packet, low priority "eventually"), and MMO area-of-interest work reports up to 6 times fewer messages. **[3rd-party]** — [Gaffer On Games](https://gafferongames.com/post/state_synchronization/); [Boulanger et al. 2006](https://www.sable.mcgill.ca/~clump/papers/boulanger-06-comparing.pdf)
- (c) View-only is slither.io's "close enough to be drawn on screen", Ogar's view box, and Roblox streaming. Roblox warns that per-viewer foci add server work about equal to extra players. **[fan/RE, official]** — [Slither.io-Protocol](https://github.com/ClitherProject/Slither.io-Protocol/blob/master/Protocol.md); [Roblox streaming](https://create.roblox.com/docs/workspace/streaming)
- (d) Event-based with local animation: no direct game precedent was found. The closest is GW2/FFXIV-style low-detail stand-ins for less relevant players. **[fan wiki, official]** — [GW2 Wiki: Culling](https://wiki.guildwars2.com/wiki/Culling); [FFXIV display limits](https://na.finalfantasyxiv.com/uiguide/faq/faq-other/setting_ch_quantity.html)
- (e) Click-to-move is Club Penguin's `sp` (x,y) message, one broadcast per move command; Habbo uses click-a-tile with pathfinding. **[fan/RE]** — [Houdini player.py](https://github.com/solero/houdini/blob/master/houdini/handlers/play/player.py); [Arcturus issue #294](https://bitbucket.org/Wesley12312/arcturus/issues/294/random-click-between-both-users)
- (f) Send only on change (a hybrid that fits joystick control): Panda3D sends only changed fields plus one "stop", and Among Us sends only `if (HasMoved())`. **[official engine source, fan/RE]** — [cDistributedSmoothNodeBase.cxx](https://github.com/panda3d/panda3d/blob/master/direct/src/distributed/cDistributedSmoothNodeBase.cxx); [Among Us CNT](https://github.com/polusgg/assets-unity/blob/master/Assets/OfficialAssets/Scripts/CustomNetworkTransform.cs)

### Inferences
Estimates below are **back-of-envelope** figures. They assume 30 heroes, 6 teams of 5, a 5 Hz per-hero live rate (165 msg/s ÷ 30 ≈ 5.5/s per hero today), and count "hero position updates each phone must receive per second". Whether the hub batches these into fewer Realtime messages, and how Supabase bills them, is outside this note.

| Option | Updates received per phone/s (est.) | Saving vs (a) | Delay potential | What players lose | Evidence/precedent |
|---|---|---|---|---|---|
| (a) Everyone live, 5 Hz | 29 × 5 = 145 | 0% | ~0.1 to 0.2 s buffer is normal | nothing | .io, Among Us, Toontown |
| (b) Team live 5 Hz + others 1 Hz | 4×5 + 25×1 = 45 | ~69% (~78% at 0.5 Hz) | team ~0.2 s; others ~1 s, smoothed | other teams' paths are coarser; looks fine if interpolated | Fiedler priority; MMO AOI; Fall Guys crowd perception |
| (c) Only heroes in camera, 5 Hz | depends on clustering; e.g. 5 to 15 visible → 25 to 75 | ~50 to 83% | same as (a) | nothing on screen; off-screen heroes not shown (or shown via minimap) | slither.io, Ogar, Roblox; Boulanger up to 6× |
| (d) Tower events only, animated locally | ~2 events per tower visit; at a 30 to 60 s round ≈ 0.03 to 0.07 per hero → ~1 to 2 total | ~99% | event arrival + walk time; heroes may "arrive" late | free roaming, wandering and idle motion of others; path is canned | no direct precedent; GW2/FFXIV low-detail stand-ins |
| (e) Click-to-move, one msg per tap | taps while moving, e.g. 0.3 to 1/s per moving hero; idle = 0 | ~80 to 95% (estimate) | one network trip, no deep buffer needed; can fast-forward by timestamp | needs tap-to-walk controls and identical pathing on all phones; joystick feel lost | Club Penguin `sp`, Habbo |
| (f) Send on change (heading/stop), dead-reckon between | only on start/turn/stop + slow heartbeat | large when heroes idle at towers (estimate) | small; prediction can extrapolate | small drift corrections on turns | Panda3D only-changed + stop; Among Us HasMoved |

- Options (b), (e) and (f) combine well. For example: own team via (f) at full fidelity, other teams via (b) at low rate or as (d)-style ghosts. Since heroes cannot collide, there is no need for deterministic physics, only identical walk speed and path rules for (e).
- Option (c) gives the biggest saving at full fidelity, but it needs a server that filters per viewer (one message per viewer per tick). On a broadcast relay that may **increase** the message count even as bytes drop. Roblox's warning about per-viewer foci cost points the same way.
- The current 1.0 to 1.2 s delay is about 5 to 10 times the 100 to 200 ms buffers used by Source, Gambetta's model, Victor Zhou and Panda3D. Sending less, as in (e) and (f), shortens the queue in front of the relay and may itself cut the delay. This needs measuring.

### Gaps
- No direct precedent was found for (d), event-only movement of other players animated locally, in a shipped multiplayer game. Turn-based or asynchronous "ghost" games (e.g. racing ghosts) were not researched.
- The savings figures are estimates from assumed rates, not measurements. They should be checked against the project's simulator (`tools/sim`).

## 7. Education and classroom games: does seeing classmates move matter for motivation?

### Takeaway
Seeing other people while playing measurably raises enjoyment: a co-located co-player "significantly adds to the fun, challenge, and perceived competence" (Gajadhar et al. 2008). Classroom products with walking avatars (Gimkit 2D, Prodigy worlds, Minecraft Education) all provide shared visible worlds, with caps of 30 to 200. However, **no study was found** that isolates "seeing classmates' avatars move live" from "knowing classmates are playing" (a leaderboard or tower markers).

### Cited Findings
- Gajadhar, de Kort & IJsselsteijn (2008), "Shared Fun Is Doubled Fun": "a co-located co-player significantly adds to the fun, challenge, and perceived competence in the game". Involvement stays the same or rises with mediated or co-located co-players compared with playing alone. **[3rd-party academic]** — [Springer chapter](https://link.springer.com/chapter/10.1007/978-3-540-88322-7_11); [Meaningful Play 2008 abstract](https://meaningfulplay.msu.edu/proceedings2008/abstract.php?paperid=44)
- Fall Guys players overestimated co-player count by about 2 times, so the *sense* of a crowd does not need every individual rendered precisely. **[3rd-party press quoting developer]** — [PCGamesN](https://www.pcgamesn.com/fall-guys/player-count)
- In SPOT, a classroom tool where students interact with classmates through animated dog avatars showing performance and emotional state, findings suggest learners "feel more connected". **[3rd-party academic, via search snippet; not read in full]** — [NSF PAR 10288797](https://par.nsf.gov/biblio/10288797)
- Gimkit makes cosmetics usable only in 2D (walking-avatar) modes, so visible avatars serve as its motivational reward. **[official]** — [Gimkit Help: 2D game modes](https://help.gimkit.com/en/article/2d-game-modes-1fhidpg/)
- Prodigy built shared worlds so players can "find their friends in game" and view their player cards. **[official per search snippet; page 404 now]** — [Prodigy blog](https://www.prodigygame.com/main-en/blog/prodigy-game-update-multiplayer-worlds)
- Minecraft Education supports whole-class worlds of up to 30, hosted from the teacher's machine. **[3rd-party]** — [Microsoft UK Stories](https://ukstories.microsoft.com/2016/11/03/minecraft-education-edition-released-help-children-learn-schools/)

### Inferences
- The social benefit seems to come from **co-presence**, from knowing classmates are there and active, more than from frame-exact motion. NumXventure's players are physically co-located, which already supplies much of the social presence that Gajadhar et al. measured. That argues the on-screen version can be low fidelity for other teams.
- The client's requirement ("all on one map and see each other") is met by options (b), (d) and (e). Option (c) meets it only if off-screen heroes still appear somewhere (minimap or edge markers).
- The strongest motivational signal is probably *teammates* and *rival teams' progress* (which tower they reached), which event-based (d) conveys well. Fine-grained walking paths of other teams likely add little; this is an inference, not tested.

### Gaps
- No study was found that measures motivation or learning when classmates' avatars are visible and moving versus static or absent in a classroom game.
- No published research was found on Prodigy's or Gimkit's design rationale for shared worlds, beyond help-center text.
